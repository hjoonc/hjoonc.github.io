## 들어가기 전

이 글은 **개발자도 알아야 할 소프트웨어 테스팅 실무**를 읽으며 공부한 내용을 정리한 글이다.

개인적인 학습 정리인 만큼 일부 내용이 정확하지 않을 수 있으며, **ISTQB 시험을 준비한다면 교재를 직접 읽어보는 것을 추천한다.**

## 1. 리뷰의 이점과 목적
- 정적 기법이란?
  
  SW를 실행하지 않고 테스팅하는 기법. 동적 테스팅과 다르게 장애보다는 **장애의 원인(결함)을 발견**하는데 집중.

- 리뷰란?

  코드를 포함하여 SW 개발 및 테스트 산출물 검토, 테스팅하는 방법. **동적 테스팅 전 수행 -> 초기 결함 수정으로 비용 절감.**

- 리뷰의 대상(계획서.설계서.TC)

  요구사항 명세, 설계 명세, 코드, 테스트 계획&명세, TC, 테스트 스크립트, 사용자 가이드, 웹페이지 등 **모든 SW 개발&테스트 산출물.**

- 리뷰의 이점

  **조기 결함 발견 및 수정, 개발 생산성 향상, 개발 기간 단축, 테스트 비용, 결함 감소, 커뮤니케이션 향상, 이해도 증진.**

- 리뷰를 통해 발견하기 쉬운 결함
  
  **표준 위반, 요구사항 결함, 개발설계 결함, 불충분한 유지 보수성, 부정확한 인터페이스 명세.**

- 페이건 인스펙션
  
  초반부터 전문 인력을 대거 투입하여 초기 불량률을 낮추거나 품질향상으로 도모하여 비용을 감소시키는 방법.

## 2. 공식 리뷰
- 공식 리뷰의 절차 (ㄱ.ㅅ.ㄱ.ㅁ.ㅈ.ㅎ)
  
  계획 활동 -> 시작 -> 개별 준비 -> 리뷰 미팅 -> 재작업 -> 후속처리 확인.
 
  - 계획 활동 : 참가인원 선정 및 역할 할당, 시작 & 종료기준 정의, 리뷰 대상 정의.&emsp;//관
  - 시작(Kick Off)미팅 : 문서 배포, 리뷰 목표/절차/문서를 참석자에게 설명.&emsp;//중.검.저
  - 개별준비 : 미팅 전 참석자별 사전 리뷰 활동을 통해 잠재적 결함이나 질의 정리.&emsp;//검
  - 리뷰 미팅 : 개별 준비 내용 토의 및 문서화&emsp;//중.검.저.기
  - 재작업 : 발견된 결함을 대상 문서의 저자가 수정&emsp;//저
  - 후속처리(follow-up) : 발견된 결함이 조치되었는지 확인&emsp;//중

 
- 공식적리뷰의 역할과 책임
  - 관리자 : 리뷰 **실행여부 결정.** 리뷰 시간 할당. 리뷰 목적 달성 여부확인 및 승인.
  - 중재자 : **문서의 리뷰를 리드.** 리뷰 계획, 미팅 진행, 후속처리 조치 여부 추적관리. **성패를 좌우.**
  - 검토자 : **테스트 전문가.** 해당 분야 기술적 배경 갖춘 사람. **인스펙터.** 인시던트 발견 & 기술. **개발자는 약점을 알기때문에 검토자가 되어서는 안됨. 테스트 용이성을 가장 먼저 확인.**
  - 저자 : 리뷰 대상 산출물을 작성한 사람 또는 책임자. **개발자.**
  - 기록자 : 모든 내용 기록, 문서화. 다른 참가자가 겸업해도 됨. 검토자는 X. 중재자는 O.

## 3. 비공식 리뷰
- 비공식적 리뷰

  공식적 절차X. 동료에 의한 리뷰, 기술선임자 리뷰. 선택적 문서화. 리뷰하는 사람에 따라 성과가 좌우됨. 저렴한 방법으로 일정 수준 성과 달성.
<br>

## 4. 추가 리뷰 방법(동료검토)
- 인스펙션(기술) : **중재자**가 주도. **결함 발견.** 동료 검사. **공식적 리뷰.**&emsp;//안전. 반드시 테스트 필요.
- 기술적 리뷰(기술) : **중자재**가 주도. **기술전문가 참여.** 공식/비공식 가능.
- 워크스루(사업) : **저자**가 주도. 오픈 세션. 공식/비공식 가능.&emsp;//인수, 저자, 고객(validation)과 관련.

## 5. 도구에 의한 정적 분석
리뷰와 마찬가지로 **결함을 발견하는데 초점.** 주로 **개발자에 의해 사용됨.**

복잡도와 같은 매트릭을 측정해 코드와 설계의 의심스러운 양상에 대해 조기 경보 제공.

변수/인터페이스/코드/코딩 표준 위반/보안 취약성/구문 규칙 위반.
<br>

## 주의
- 리뷰와 정적 분석 도구는 다른 것이다.
- 감사 : 독립적으로 프로세스, 규정, 표준의 준수 여부를 판단한다.
