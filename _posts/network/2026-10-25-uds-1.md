## UDS on CAN

**UDS**(**Unified Diagnostic Services**)는 ISO 14229에 정의된 **차량 진단 통신 프로토콜**이다. <br>
ECU와 진단기(Tester) 사이에서 **고장 코드 조회, 데이터 읽기·쓰기, ECU 제어** 등의 기능을 수행한다.

**UDS on CAN**은 CAN 통신 환경에서 UDS를 사용하는 방식으로, <br>
**ISO-TP**(**ISO 15765-2**)를 이용하여 진단 메시지를 전송한다.

## Addressing

UDS의 Addressing 방식은 **Physical Addressing**과 **Functional Addressing**으로 구분된다.

### 1. Physical Addressing

**특정 ECU 하나를 대상으로 진단 요청을 전송**하는 방식이다.

예를 들어 VCU, BMS, MCU 중 **VCU에만 진단 명령을 전송**하는 경우에 해당한다.

```text
Tester → VCU : 0x710
VCU → Tester : 0x718
```

### 2. Functional Addressing

**여러 ECU를 대상으로 동일한 진단 요청을 전송**하는 방식이다.

단, 해당 Functional Address를 수신하도록 설정된 ECU만 요청을 처리하며, <br>
**모든 ECU가 반드시 응답하는 것은 아니다.**

```text
Tester → ECUs : 0x7DF
```

CAN ID는 설명을 위한 예시이며, 실제 CAN ID는 시스템별로 다를 수 있다. <br>
특히 `0x7DF`는 **11-bit OBD Functional Address의 대표적인 예시**이다.

## Frame

UDS on CAN에서는 **ISO-TP**를 이용하여 진단 데이터를 전송한다.

Classic CAN에서는 하나의 CAN 프레임에 **최대 8바이트의 데이터**를 담을 수 있으며, <br>
진단 데이터의 크기에 따라 **Single Frame**과 **Multi Frame**으로 구분된다.

이하 예시는 **Classic CAN, Normal Addressing, 8바이트 프레임**을 기준으로 한다.

### 1. Frame 구조

ISO-TP는 **PCI**(**Protocol Control Information**)를 이용하여 Frame의 종류와 전송 정보를 구분한다.

PCI의 첫 번째 바이트에서 **상위 4비트(Bit 7~4)는 Frame Type**을 나타내며, <br>
**하위 4비트(Bit 3~0)는 Frame 종류에 따라 서로 다른 정보**를 나타낸다.

| **Frame** | **Byte 1 (상위 4비트 / 하위 4비트)** | **Byte 2** | **Byte 3** | **Byte 4~8** |
|---|---|---|---|---|
| Single Frame (SF) | 0x0 / SF_DL | DATA1 | DATA2 | DATA3~7 |
| First Frame (FF) | 0x1 / FF_DL 상위 4비트 | FF_DL 하위 8비트 | DATA1 | DATA2~6 |
| Consecutive Frame (CF) | 0x2 / SN | DATA1 | DATA2 | DATA3~7 |
| Flow Control (FC) | 0x3 / FS | BS | STmin | Padding 또는 미사용 |


**주요 파라미터**

| 항목 | 의미 |
|---|---|
| PCI | Protocol Control Information |
| SF_DL | Single Frame Data Length |
| FF_DL | First Frame Data Length |
| SN | Sequence Number |
| FS | Flow Status |
| BS | Block Size |
| STmin | Separation Time minimum |

### 2. Single Frame (SF)

**하나의 CAN 프레임으로 진단 데이터를 전송**하는 방식이다.

일반적인 Classic CAN의 Normal Addressing에서는 1바이트의 PCI를 사용하므로, <br>
**최대 7바이트의 UDS 데이터**를 전송할 수 있다.

**예시: Extended Session 진입 요청 및 응답**

```text
Tester → ECU (Request)
02 10 03 00 00 00 00 00

ECU → Tester (Response)
06 50 03 00 32 01 F4 00
```

**Request**

| Byte | 값 | 설명 |
|---|---|---|
| 1 | 0x02 | SF, 데이터 길이 2바이트 |
| 2 | 0x10 | DiagnosticSessionControl |
| 3 | 0x03 | Extended Session |
| 4~8 | 0x00 | Padding |

**Response**

| Byte | 값 | 설명 |
|---|---|---|
| 1 | 0x06 | SF, 데이터 길이 6바이트 |
| 2 | 0x50 | Positive Response SID |
| 3 | 0x03 | Extended Session |
| 4~5 | 0x0032 | P2Server_max = 50ms |
| 6~7 | 0x01F4 | P2*Server_max = 5,000ms |
| 8 | 0x00 | Padding |

첫 번째 바이트는 **PCI**(**Protocol Control Information**)이며, <br>
상위 4비트는 **Frame Type**, 하위 4비트는 **데이터 길이**(**SF_DL**)를 나타낸다.

**PCI 해석**

```text
Request  : 0x02 = 0000 0010
Response : 0x06 = 0000 0110

                 Bit 7~4  Bit 3~0
                    ↓        ↓
                  Type     SF_DL
```

- **Request:** Type = 0x0 (SF), SF_DL = 2바이트
- **Response:** Type = 0x0 (SF), SF_DL = 6바이트

즉, **Request와 Response 모두 하나의 CAN 프레임으로 전송**되며, <br>
각 프레임의 **SF_DL은 해당 프레임에 포함된 UDS 데이터 길이**를 나타낸다.

### 3. Multi Frame

진단 데이터가 하나의 CAN 프레임에 들어가지 않을 때, <br>
**여러 프레임으로 분할하여 전송**하는 방식이다.

Multi Frame은 **First Frame**(**FF**), **Flow Control**(**FC**), **Consecutive Frame**(**CF**)으로 구성된다.

| Frame | 역할 |
|---|---|
| First Frame (FF) | 전체 데이터 길이 및 초기 데이터 전달 |
| Flow Control (FC) | 수신 측에서 전송 흐름 제어 |
| Consecutive Frame (CF) | 나머지 데이터 전달 |

**통신 순서**

```text
Sender                         Receiver
   |                               |
   |-------- First Frame --------->|
   |                               |
   |<------- Flow Control ---------|
   |                               |
   |------ Consecutive Frame ----->|
   |------ Consecutive Frame ----->|
   |              ...              |
```

#### 3.1 First Frame (FF)

**전체 UDS 데이터 길이와 초기 데이터를 전달**하는 프레임이다.

일반적인 Classic CAN의 12-bit FF_DL 형식에서는 <br> 
**첫 2바이트**에 **Frame Type**과 **전체 데이터 길이**(**FF_DL**)가 포함된다.

**예시: 전체 UDS 데이터 길이 20바이트**

```text
10 14 62 F1 90 11 22 33
```

| Byte | 값 | 설명 |
|---|---|---|
| 1 | 0x10 | FF Type 및 FF_DL 상위 4비트 |
| 2 | 0x14 | FF_DL 하위 8비트 |
| 3 | 0x62 | Positive Response SID |
| 4~5 | 0xF190 | DID |
| 6~8 | 0x11 22 33 | 초기 데이터 |

**PCI 해석**

첫 두 바이트 `0x10, 0x14`을 비트 단위로 표현하면 다음과 같다.

```text
Byte1 = 0x10 = 0001 0000
               └──┘ └──┘
               Type FF_DL 상위 4비트

Byte2 = 0x14 = FF_DL 하위 8비트
```

- **Frame Type:** 0x1 (First Frame)
- **FF_DL:** 0x014 (20바이트)

즉, `10 14`는 **전체 UDS 데이터 길이가 20바이트**임을 의미한다.

이는 **FF와 이후 CF를 통해 전달할 전체 UDS 메시지의 길이**이다. <br>
일반적인 Classic CAN의 FF는 **2바이트 PCI + 6바이트 UDS 데이터**로 구성된다.

#### 3.2 Flow Control (FC)

Receiver가 First Frame을 수신한 후, <br>
**Sender의 데이터 전송을 제어하기 위해 전송**하는 프레임이다.

**예시: Flow Control**

```
30 00 0A 00 00 00 00 00
```

| **Byte** | **값** | **설명** |
|---|---|---|
| 1 | 0x30 | FC Type + FS (0x0: CTS - 전송 허용, 0x1: WT - 전송 대기, 0x2: OVFLW - 수신 불가) |
| 2 | 0x00 | BS (추가 FC 없이 연속 전송할 수 있는 CF 개수) |
| 3 | 0x0A | STmin (연속된 CF 사이의 최소 전송 간격) |
| 4~8 | 0x00 | Padding |

**PCI 및 파라미터 해석**

```
0x30 = 0011 0000
       └──┘ └──┘
       Type  FS

Type  = 0x3 (Flow Control)
FS    = 0x30 & 0x0F = 0x0 (CTS)
BS    = 0x00 (제한 없음)
STmin = 0x0A (10ms)
```

즉, 위 예시는 **데이터 전송을 허용**(**CTS**)하며, <br>
**추가 FC 없이 남은 CF를 전송**(**BS = 0**)하고, **CF 간 최소 10ms의 간격**(**STmin**)을 유지하도록 요청하는 프레임이다.

#### 3.3 Consecutive Frame (CF)

Sender가 Flow Control 조건에 따라 **나머지 데이터를 전송**하는 프레임이다.

```text
21 44 55 66 77 88 99 AA
```

| Byte | 값 | 설명 |
|---|---|---|
| 1 | 0x21 | CF Type + SN |
| 2~8 | 0x44 55 66 77 88 99 AA | UDS 데이터 |

첫 번째 바이트 `0x21`은 다음과 같다.

```text
0x21 = 0010 0001
       └──┘ └──┘
       Type  SN

Type = 0x2 (Consecutive Frame)
SN   = 0x1 (Sequence Number 1)
```

**Sequence Number**(**SN**)는 CF의 전송 순서를 나타내며, <br>
첫 번째 CF는 일반적으로 `0x21`, 두 번째 CF는 `0x22`로 시작한다.

### 4. Multi Frame 통신 예시 (ECU → Tester)

**0x22**(**ReadDataByIdentifier**)를 이용하여 진단기가 ECU의 데이터를 조회하는 경우이다.

조회 요청은 Single Frame으로 전송되지만, 응답 데이터가 길어 **ECU가 Multi Frame으로 응답**하는 상황이다.

```text
Tester → ECU (Request)
03 22 12 34 00 00 00 00

ECU → Tester (FF)
10 14 62 12 34 11 22 33

Tester → ECU (FC)
30 00 0A 00 00 00 00 00

ECU → Tester (CF1)
21 44 55 66 77 88 99 AA

ECU → Tester (CF2)
22 BB CC DD EE FF 00 11
```

**Request**

```text
03 22 12 34 00 00 00 00
```

- **0x03:** Single Frame, 데이터 길이 3바이트
- **0x22:** ReadDataByIdentifier
- **0x1234:** DID

**Response**

전체 UDS 데이터는 다음과 같이 복원된다.

```text
62 12 34 11 22 33
44 55 66 77 88 99 AA
BB CC DD EE FF 00 11
```

- **FF:** 6바이트
- **CF1:** 7바이트
- **CF2:** 7바이트
- **전체:** 20바이트

**FF_DL 계산**

```text
FF_DL = ((0x10 & 0x0F) << 8) | 0x14
      = 0x014
      = 20 bytes
```

즉, ECU는 **전체 20바이트의 UDS 응답 데이터를 FF와 CF로 분할하여 전송**한다.

### 5. Multi Frame 통신 예시 (Tester → ECU)

**0x2E**(**WriteDataByIdentifier**)를 이용하여 진단기가 ECU에 데이터를 기록하는 경우이다.

전송할 UDS 데이터가 **13바이트**라고 가정한다.

```text
Tester → ECU (FF)
10 0D 2E 12 34 11 22 33

ECU → Tester (FC)
30 00 00 00 00 00 00 00

Tester → ECU (CF1)
21 44 55 66 77 88 99 AA

ECU → Tester (Response)
03 6E 12 34 00 00 00 00
```

**First Frame**

```text
10 0D 2E 12 34 11 22 33
```

| Byte | 값 | 설명 |
|---|---|---|
| 1 | 0x10 | FF Type 및 FF_DL 상위 4비트 |
| 2 | 0x0D | FF_DL 하위 8비트 |
| 3 | 0x2E | WriteDataByIdentifier |
| 4~5 | 0x1234 | DID |
| 6~8 | 0x11 22 33 | 초기 데이터 |

**FF_DL 계산**

```text
FF_DL = ((0x10 & 0x0F) << 8) | 0x0D
      = 0x00D
      = 13 bytes
```

**전체 UDS 데이터**

```text
2E 12 34 11 22 33
44 55 66 77 88 99 AA
```

- **FF:** 6바이트
- **CF1:** 7바이트
- **전체:** 13바이트

ECU는 전체 데이터를 수신하고 기록 처리를 완료한 후, **Positive Response**(**0x6E**)를 전송한다.

따라서 **First Frame은 ECU만 전송하는 것이 아니라, 데이터 길이에 따라 Tester와 ECU 모두 전송할 수 있다.**

※ DID `0x1234` 및 데이터 값은 설명을 위한 가상 예시이다.

## 정리

- **Physical Addressing:** 특정 ECU 대상
- **Functional Addressing:** 여러 ECU 대상
- **Single Frame:** 하나의 프레임으로 전송
- **First Frame:** 전체 데이터 길이와 초기 데이터 전달
- **Flow Control:** Receiver가 전송 조건 제어
- **Consecutive Frame:** 나머지 데이터 전송

ISO-TP에서는 **PCI 상위 4비트로 Frame Type을 구분**하며, <br>
Frame 종류에 따라 **SF_DL, FF_DL, FS, BS, STmin, SN** 등의 정보를 사용한다.

**Multi Frame은 요청과 응답 모두에 사용될 수 있으며**, <br>
통신 분석 시 **FF_DL, BS, STmin, Sequence Number**를 확인하는 것이 중요하다.
