## SID (Service Identifier)

**SID**(**Service Identifier**)는 UDS에서 **진단 서비스의 종류를 구분하는 1바이트 식별자**이다.

진단기(Tester)는 SID를 통해 ECU에 수행할 기능을 요청하며, <br>
ECU는 요청 처리 결과에 따라 **Positive Response** 또는 **Negative Response**를 전송한다.

이하 예시는 **Classic CAN, Normal Addressing, 8바이트 프레임**을 기준으로 한다.

### 1. 주요 SID

| **SID** | **서비스** | **기능** |
|---|---|---|
| 0x10 | DiagnosticSessionControl | 진단 세션 변경 |
| 0x11 | ECUReset | ECU 재시작 |
| 0x14 | ClearDiagnosticInformation | DTC 삭제 |
| 0x19 | ReadDTCInformation | DTC 정보 조회 |
| 0x22 | ReadDataByIdentifier | DID 데이터 읽기 |
| 0x27 | SecurityAccess | 보안 접근 |
| 0x2E | WriteDataByIdentifier | DID 데이터 쓰기 |
| 0x2F | InputOutputControlByIdentifier | ECU 입출력 제어 |
| 0x31 | RoutineControl | ECU 내부 루틴 실행 |
| 0x3E | TesterPresent | 진단 세션 유지 |

각 SID는 고유한 진단 기능을 나타내며, <br>
서비스에 따라 **Sub-Function, DID 등의 추가 파라미터**를 사용한다.

### 2. SID 위치

#### 2.1 Single Frame

일반적인 진단 요청은 **Single Frame으로 전송되는 경우가 많다.**

**예시: ReadDataByIdentifier (0x22)**

```text
Tester → ECU (Request)
03 22 F1 90 00 00 00 00
```

| **Byte** | **값** | **설명** |
|---|---|---|
| 1 | 0x03 | PCI (Single Frame, 데이터 길이 3바이트) |
| 2 | 0x22 | SID (ReadDataByIdentifier) |
| 3~4 | 0xF190 | DID |
| 5~8 | 0x00 | Padding |

즉, **Single Frame에서는 PCI가 1바이트이므로 SID가 Byte 2에 위치**한다.

#### 2.2 Multi Frame

요청 데이터가 하나의 CAN 프레임에 들어가지 않는 경우에는 **Multi Frame으로 전송**한다. <br>
데이터 쓰기, 보안 인증, 펌웨어 전송 등 요청 데이터가 긴 경우에는 **Multi Frame이 사용될 수 있다.**

**예시: WriteDataByIdentifier (0x2E)**

```text
Tester → ECU (FF)
10 0D 2E 12 34 11 22 33

ECU → Tester (FC)
30 00 00 00 00 00 00 00

Tester → ECU (CF1)
21 44 55 66 77 88 99 AA
```

| **Byte** | **값** | **설명** |
|---|---|---|
| 1~2 | 0x10 0D | PCI (First Frame, 전체 데이터 길이 13바이트) |
| 3 | 0x2E | SID (WriteDataByIdentifier) |
| 4~5 | 0x1234 | DID |
| 6~8 | 0x11 22 33 | 초기 데이터 |

즉, **First Frame에서는 PCI가 2바이트이므로 SID가 Byte 3에 위치**한다.

이후 전송되는 **Consecutive Frame에는 별도의 SID가 포함되지 않으며**, <br>
Receiver는 FF와 CF의 데이터를 결합하여 하나의 UDS 메시지로 복원한다.

### 3. Positive Response

ECU가 진단 요청을 정상적으로 처리한 경우 전송하는 **긍정 응답**이다.

일반적으로 **Positive Response SID는 Request SID에 0x40을 더한 값**이다.

**예시: DiagnosticSessionControl (0x10)**

```text
Tester → ECU (Request)
02 10 03 00 00 00 00 00

ECU → Tester (Positive Response)
06 50 03 00 32 01 F4 00
```

**Request**

| **Byte** | **값** | **설명** |
|---|---|---|
| 1 | 0x02 | PCI (Single Frame, 데이터 길이 2바이트) |
| 2 | 0x10 | Request SID (DiagnosticSessionControl) |
| 3 | 0x03 | Sub-Function (Extended Session) |
| 4~8 | 0x00 | Padding |

**Positive Response**

| **Byte** | **값** | **설명** |
|---|---|---|
| 1 | 0x06 | PCI (Single Frame, 데이터 길이 6바이트) |
| 2 | 0x50 | Positive Response SID |
| 3 | 0x03 | Sub-Function (Extended Session) |
| 4~5 | 0x0032 | P2Server_max = 50ms |
| 6~7 | 0x01F4 | P2*Server_max = 5,000ms |
| 8 | 0x00 | Padding |

**SID 계산**

```text
Positive Response SID = Request SID + 0x40

                      = 0x10 + 0x40
                      = 0x50
```

즉, ECU가 **Extended Session 진입 요청을 정상적으로 처리**했음을 의미한다.

### 4. Negative Response

ECU가 진단 요청을 정상적으로 처리할 수 없는 경우 전송하는 **부정 응답**이다.

Negative Response는 **Negative Response SID(0x7F), Request SID, NRC**가 순서대로 포함된 구조이다.

```text
[Negative Response SID] [Request SID] [NRC]
         0x7F
```

여기서 **NRC**(**Negative Response Code**)는 요청을 처리할 수 없는 원인을 나타내는 **1바이트 코드**이다.

**주요 NRC**

| **NRC** | **이름** | **의미** |
|---|---|---|
| 0x11 | serviceNotSupported | 요청한 SID를 지원하지 않음 |
| 0x12 | subFunctionNotSupported | 요청한 Sub-Function을 지원하지 않음 |
| 0x13 | incorrectMessageLengthOrInvalidFormat | 요청 메시지의 길이 또는 형식이 잘못됨 |
| 0x22 | conditionsNotCorrect | 요청 수행 조건이 충족되지 않음 |
| 0x31 | requestOutOfRange | 요청한 파라미터 또는 데이터가 허용 범위를 벗어남 |
| 0x33 | securityAccessDenied | 보안 접근 조건이 충족되지 않음 |
| 0x78 | requestCorrectlyReceived-ResponsePending | 요청을 수신했지만 처리가 완료되지 않아 응답 대기 중 |

**예시: 지원하지 않는 Sub-Function 요청**

```text
Tester → ECU (Request)
02 10 05 00 00 00 00 00

ECU → Tester (Negative Response)
03 7F 10 12 00 00 00 00
```

**Request**

| **Byte** | **값** | **설명** |
|---|---|---|
| 1 | 0x02 | PCI (Single Frame, 데이터 길이 2바이트) |
| 2 | 0x10 | Request SID (DiagnosticSessionControl) |
| 3 | 0x05 | 지원하지 않는 Sub-Function (예시) |
| 4~8 | 0x00 | Padding |

**Negative Response**

| **Byte** | **값** | **설명** |
|---|---|---|
| 1 | 0x03 | PCI (Single Frame, 데이터 길이 3바이트) |
| 2 | 0x7F | Negative Response SID |
| 3 | 0x10 | 요청했던 SID (DiagnosticSessionControl) |
| 4 | 0x12 | NRC (subFunctionNotSupported) |
| 5~8 | 0x00 | Padding |

**응답 해석**

```text
03 7F 10 12 00 00 00 00
   └─┘ └─┘ └─┘
    │   │   └─ NRC = 0x12
    │   └───── Request SID = 0x10
    └───────── Negative Response SID = 0x7F
```

즉, ECU는 **0x10 서비스 요청은 수신했지만, 요청한 Sub-Function 0x05를 지원하지 않는다**는 의미로 응답한다.

※ NRC `0x78`은 최종적인 실패를 의미하지 않으며, **요청 처리 중이므로 최종 응답을 기다려야 한다**는 의미이다. <br>
※ DID `0x1234`와 기록 데이터는 가상 예시이며, 해당 DID가 쓰기를 지원하는 상황을 가정한다.
